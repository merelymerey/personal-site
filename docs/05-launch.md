## 2. Deployment steps actually performed

1. `python3 -m unittest discover tests -v`: 60 tests passed; this also built `dist/`.
2. `dist/` zipped (34 entries, 164 KB) including the hidden `.htaccess` and `data/.htaccess`.
3. In the InfinityFree dashboard a free hosting account was created with the subdomain `merey.freedev.app`. The account password was generated by InfinityFree.
4. File Manager, folder `htdocs/`, "Upload & Unzip".
5. The HTTPS address was opened and checks H-01 to H-15 were run.
6. The privacy statement was updated for the host's cookie (D-14), the site was rebuilt and uploaded again, and the release was tagged.

## 3. Hosting limitations found

| Limitation | Effect | How it is handled |
|---|---|---|
| Anti-bot check | InfinityFree answers the first request of every visitor with a small JavaScript challenge that sets a cookie named `__test`. Clients without JavaScript, including `curl` and some link checkers, get an empty reply. | Disclosed in the privacy statement; hosted tests are run in a real browser; recorded as D-14 |
| No outgoing e-mail on the free plan | The form cannot notify the author | Messages are stored in a closed file and read through the File Manager |
| DNS propagation | The host warns that a new subdomain can take up to 72 hours to be reachable everywhere | The site answered within minutes from Almaty; re-check from the tester's network |
| Certificate and uptime controlled by the host | A lapse cannot be fixed by the author | HSTS deliberately not enabled; source is on GitHub and can be redeployed elsewhere |
| Advertising in the dashboard | Full-page adverts appear in the control panel (not on the site) | None needed; no advert is shown to visitors |
| Default file | The host places `index2.html` in `htdocs/` | Left in place; it is not linked and `index.html` takes precedence |
| PHP only | No Python or Node on the server | The site is built locally; only `contact.php` runs on the host |

## 4. Known limitations of the site

- The Kazakh and Russian texts were written with AI assistance and still need the author's line-by-line review before the demonstration.
- Manual testing with another person is prepared (script in `docs/04-testing.md`) but had not taken place when this document was written.
- Browser testing so far covers Chrome on desktop and an emulated phone; Safari, Firefox and a real phone are part of the manual session.
- The contact form's storage is capped at 1 MB and has no notification; messages must be checked by hand.
- Without JavaScript the pages themselves work, but the host's challenge prevents reaching them.
- All subjects in the learning portfolio are in progress, so the page shows no completed coursework yet.

## 5. Reflection

The first prompt of this project was one line: read the assignment, ask me questions first, then do everything. The useful part of that prompt turned out to be "ask me first". The assistant came back with nineteen questions, and answering them forced decisions I had not thought about: whether my student ID should appear in a web address, whether a photo of me was needed at all, and which of my projects I could actually explain in front of the teacher. One project the assistant had on its list was a Telegram bot it knew nothing about. Instead of describing it from imagination, it asked, and then checked the running bot in Telegram before writing a word. That set the rule for the rest of the work: nothing goes on the site that cannot be traced to something real.

The first generated version was complete but plain, and my own prompts about it were the weakest of the project. "Make it more beautiful" produced a change I still did not like, and I had to say it three more ways (as a landing page, without the ornament, with a different colour, with a picture of KBTU) before the result matched what I had in mind. Compared with the prompts that carried requirement IDs, a repository map and constraints, which worked on the first attempt, this showed me what context engineering means in practice: the model was never the problem, the missing information was.

What I verified myself is narrower than what the tools verified, and I want to be exact about that. Sixty automated tests pass, and fifteen checks were run on the live address, including a real form submission with Kazakh letters. The code review found twenty-three issues in the first version; twelve were confirmed in the code and fixed, one was wrong, and one suggested fix (a year-long HSTS header on a host whose certificate I do not control) was rejected. The picture I had saved from an image search was not used, because nobody could say who owned it; a freely licensed photograph with credit replaced it. I can explain these decisions. What I cannot yet claim is that the Kazakh text reads naturally to a native speaker, or that the site works on a real phone in someone else's hands. Both are still to be done by me, not by a tool.

The hosting taught the last lesson. The requirements said "no cookies", and the code sets none, but InfinityFree sets one for its own protection. The honest fix was to change the requirement and the privacy statement, not to keep a sentence that had become untrue.

The remaining limitations are listed above. The next improvement is clear: run the session with another person on a phone, fix what they trip over, and replace the "in progress" list with subjects I have completed, each linked to one piece of work. After that I would add notification for new messages, so the form is something I really use.
